<details>
<summary>📋 Guidance</summary>

**Purpose:** The Change Register provides a consolidated view of all Architecture Change Requests (ACR-NNN) for this engagement — their status, disposition, and impact on the architecture repository. It enables architecture governance authorities to monitor the change portfolio and identify patterns (e.g. repeated requests in the same domain signalling a design issue).

**What to include:** All ACR-NNN entries, with their current status (Proposed / Under Review / Approved / Rejected / Deferred), disposition date, impact domains, and whether the required artifact updates have been completed. This register is generated by `/ea-changes` from source ACR artifacts — do not edit it manually.

**Quality indicators:**
- Approved ACRs have a corresponding artifact update status — approved changes without artifact updates represent architecture drift
- The register is regenerated before every governance review — stale registers misrepresent the change portfolio
- Change patterns are visible: if 5+ ACRs target the same domain, that domain's architecture may have a design gap worth investigating

**Common mistakes:**
- Using the Change Register as the primary record — all changes are authored in ACR-NNN artifact files; the register is a view
- Marking Approved ACRs as complete before the required artifact updates are done — completeness should require artifact updates, not just approval
- Not using the register to spot patterns — the register is a diagnostic tool, not just an audit log

**TOGAF reference:** TOGAF 10 Part III, Phase H (§33) — Architecture Change Management. The Change Register is the Phase H governance artifact that tracks the evolution of the architecture repository post-delivery.

</details>
