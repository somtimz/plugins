<details>
<summary>📋 Guidance</summary>

The Use Cases Register captures all actor-goal interactions for this engagement.

A Use Case is a **discrete unit of interaction** between an actor and the business/system to achieve a goal. It defines preconditions, a main flow of actor actions and system/business responses, and postconditions. Use Cases answer *"what does the actor want to achieve?"* — distinct from Business Processes (*"how the organisation performs work"*) and User Stories (*"small backlog items"*).

Capture every use case with:
  - **Name** — goal-oriented verb phrase (e.g. "Submit Claim")
  - **Actor** — primary user or external system
  - **Goal** — the measurable outcome
  - **Preconditions / Postconditions**
  - **Main Flow** — numbered actor action ↔ system/business response
  - **Alternative / Exception Flows**
  - **Linked Requirements** — REQ-NNN IDs the use case realises
  - **Linked Business Processes** — PROC-NNN IDs the use case triggers or participates in
  - **Linked Capabilities / Value Streams** — CAP-NNN / VS-NNN IDs

**Traceability:**
  - Use Cases trace to Requirements, Processes, Capabilities, and Value Streams.
  - Use `/ea-usecases trace` to verify linkages.

**Quality indicators:**
- Every use case has a clear actor and goal
- Main flow is numbered and alternates actor action / system response
- Preconditions and postconditions are explicit
- Use cases link to at least one requirement, process, capability, or value stream
- High-priority use cases have acceptance criteria or linked requirements

**Common mistakes:**
- Confusing a use case with a process step — a use case may span multiple processes
- Writing UI instead of intent — "user clicks button" is not a goal
- Missing alternative flows — exceptions are where architecture risk lives
- Missing trace to requirements — orphan use cases cannot be validated

**TOGAF reference:** TOGAF 10 §22 — Business Architecture. Use cases bridge business requirements and application/system design.

</details>
