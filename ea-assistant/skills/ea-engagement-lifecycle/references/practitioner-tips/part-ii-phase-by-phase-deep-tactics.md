# Part II: Phase-by-Phase Deep Tactics


### Preliminary Phase — Architecture Capability

**Tactic P1:** Treat the Architecture Board as a *decision marketplace*, not a review committee.  
**Tactic P2:** Define architecture services (e.g., roadmap shaping, solution advisory) with SLAs — operate like a product team.  
**Tactic P3:** Fund architecture as a persistent capability, not a project overhead.  
**Tactic P4:** Build a minimal but enforceable standards catalog — start small, evolve fast.  
**Tactic P5:** Align architecture KPIs with enterprise OKRs (e.g., reuse rate, time-to-decision).

### Phase A — Architecture Vision

**Tactic A1:** Use "strategic tension" (current vs desired state) to drive urgency — quantify the gap.  
**Tactic A2:** Build multiple candidate visions and force trade-off discussions early.  
**Tactic A3:** Validate vision with real delivery constraints (skills, vendors, legacy).  
**Tactic A4:** Co-create the vision with business leaders to secure ownership.  
**Tactic A5:** Define success metrics *before* moving to Phase B.

### Phase B — Business Architecture

**Tactic B1:** Map capabilities to value streams — don’t model capabilities in isolation.  
**Tactic B2:** Identify differentiating vs commodity capabilities — optimize investment accordingly.  
**Tactic B3:** Use business architecture to challenge org design, not just reflect it.  
**Tactic B4:** Link capabilities directly to KPIs and revenue/cost drivers.  
**Tactic B5:** Focus on "where to play" and "how to win" — not just process diagrams.

### Phase C — Information Systems (Data + Application)

**Tactic C1:** Treat data as a product — assign ownership and lifecycle accountability.  
**Tactic C2:** Design for data interoperability early — avoid downstream integration pain.  
**Tactic C3:** Rationalize applications using measurable criteria (cost, usage, redundancy).  
**Tactic C4:** Push toward domain-oriented architectures (e.g., domain-driven design).  
**Tactic C5:** Define clear boundaries between systems — minimize coupling.

### Phase D — Technology Architecture

**Tactic D1:** Standardize platforms where it creates leverage, not where it limits innovation.  
**Tactic D2:** Use "golden paths" (approved stacks) to guide teams without forcing compliance.  
**Tactic D3:** Design for observability and operability — not just functionality.  
**Tactic D4:** Incorporate resilience (failure modes, recovery) as a first-class concern.  
**Tactic D5:** Treat cloud adoption as an operating model shift, not just a hosting change.

### Phase E — Opportunities & Solutions

**Tactic E1:** Package initiatives as value increments, not technical workstreams.  
**Tactic E2:** Prioritize by business impact × feasibility — not architecture elegance.  
**Tactic E3:** Identify quick wins that validate the target architecture early.  
**Tactic E4:** Build transition architectures deliberately — don’t skip them.  
**Tactic E5:** Use solution options to expose trade-offs clearly to stakeholders.

### Phase F — Migration Planning

**Tactic F1:** Optimize sequencing for value delivery, not technical dependency alone.  
**Tactic F2:** Actively manage risk exposure across the roadmap.  
**Tactic F3:** Align roadmap with funding cycles and budget constraints.  
**Tactic F4:** Define "exit criteria" for legacy systems — avoid indefinite coexistence.  
**Tactic F5:** Maintain roadmap flexibility — expect change.

### Phase G — Implementation Governance

**Tactic G1:** Shift from compliance policing to embedded guidance.  
**Tactic G2:** Use automated checks (CI/CD) to enforce standards where possible.  
**Tactic G3:** Focus reviews on high-risk/high-impact decisions only.  
**Tactic G4:** Track deviations explicitly and decide whether to accept or remediate.  
**Tactic G5:** Measure conformance by outcomes, not checklist completion.

### Phase H — Architecture Change Management

**Tactic H1:** Treat architecture as a living system — continuously evolve it.  
**Tactic H2:** Monitor leading indicators (tech debt, delivery friction) for change triggers.  
**Tactic H3:** Run lightweight "mini-ADM cycles" for incremental changes.  
**Tactic H4:** Retire obsolete architectures actively — don’t let them linger.  
**Tactic H5:** Feed implementation learnings back into principles and standards.
